# Requirements

## Introduction

The authentication management feature provides the
`codecraftai-sysman-linux-redhat` package with the ability to manage the
local authentication stack on Red Hat Linux systems: the PAM module
graph, the active `authselect` profile, password-quality policy,
failed-login lockout, and resource limits.

A maintenance coordinator uses this feature to bring a system's
authentication posture into a declared desired state.  All commands
(`authselect`, `pam_pwquality` tooling, `faillock`) are executed
through the `codecraftai-interfaces` command-runner abstraction.  All
reads and writes against `/etc/pam.d/*`,
`/etc/security/faillock.conf`, `/etc/security/pwquality.conf`,
`/etc/security/limits.conf`, and `/etc/security/limits.d/*` are
routed through the runner (`cat`/`tee`).  All mutating operations
respect dry-run mode.

This feature complements — and does not duplicate — the SSH-daemon
hardening surface owned by `3-ssh-server-configuration`, the
local-account surface owned by `3-user-group-management`, and the
enterprise-directory integration surface owned by
`3-identity-management`.  PAM is the glue between them.

## Requirements

### Requirement 1: Query and Select the Active `authselect` Profile

**User Story:** As a maintenance coordinator, I want to query and
switch the active `authselect` profile, so that the system's PAM
stack uses a consistent, version-managed baseline rather than
hand-edited `/etc/pam.d/*` files.

#### Acceptance Criteria

1. WHEN the coordinator queries the current profile THE SYSTEM SHALL
   invoke `authselect current` via the command runner and return a
   `AuthselectProfile` record with `id`, `features`, and the raw
   output lines.
2. WHEN the coordinator selects a profile THE SYSTEM SHALL invoke
   `authselect select <profile> [--force]` with the declared feature
   flags.
3. WHEN the current profile and feature set already match the
   request THE SYSTEM SHALL skip the `select` invocation and return
   an `AuthActionResult` with status `SKIPPED`.
4. WHEN dry-run mode is active THE SYSTEM SHALL NOT execute any
   command.
5. WHEN `authselect list` is requested THE SYSTEM SHALL return the
   list of available profile ids.

---

### Requirement 2: Manage `authselect` Feature Flags

**User Story:** As a maintenance coordinator, I want to enable or
disable individual `authselect` features without switching profiles,
so that I can fine-tune behaviour (e.g. `with-sudo`, `with-faillock`,
`with-fingerprint`) on top of an existing profile.

#### Acceptance Criteria

1. WHEN the coordinator enables a feature THE SYSTEM SHALL invoke
   `authselect enable-feature <feature>`.
2. WHEN the coordinator disables a feature THE SYSTEM SHALL invoke
   `authselect disable-feature <feature>`.
3. WHEN the feature is already in the requested state THE SYSTEM
   SHALL skip the operation and return `SKIPPED`.
4. WHEN the operation completes successfully THE SYSTEM SHALL run
   `authselect apply-changes` if the caller requested persistence.

---

### Requirement 3: Write Direct PAM Drop-Ins

**User Story:** As a maintenance coordinator, I want to append
custom lines into specific PAM service stacks (`/etc/pam.d/<service>`)
or author PAM drop-ins under `/etc/pam.d/<service>.d/`, so that I can
apply policy that `authselect` doesn't express.

#### Acceptance Criteria

1. WHEN the coordinator writes a PAM service file THE SYSTEM SHALL
   read the current content via `cat`, compare to the desired content,
   and skip the write when they match.
2. WHEN the desired content differs THE SYSTEM SHALL write via `tee`
   with elevation, honouring dry-run.
3. WHEN the coordinator queries a PAM service file THE SYSTEM SHALL
   return its raw content or an empty string when the file does not
   exist.
4. THE SYSTEM SHALL NOT overwrite a service file whose first comment
   line contains the marker `# Generated by authselect` unless the
   caller explicitly sets `allow_overwrite_authselect=True`, to
   prevent silent divergence from the authselect-managed baseline.

---

### Requirement 4: Password Quality Policy (`pam_pwquality`)

**User Story:** As a maintenance coordinator, I want to set
password-quality policy directives so that new passwords must meet
declared strength requirements.

#### Acceptance Criteria

1. WHEN the coordinator sets a directive THE SYSTEM SHALL upsert the
   `key = value` line in `/etc/security/pwquality.conf`, preserving
   all other lines and comments.
2. WHEN a directive's value already matches the requested value THE
   SYSTEM SHALL return `SKIPPED`.
3. WHEN the coordinator removes a directive THE SYSTEM SHALL strip
   the matching `key = ...` line and return `SUCCESS`, or `SKIPPED`
   when the directive is already absent.
4. WHEN the coordinator queries the current policy THE SYSTEM SHALL
   return a `dict[str, str]` parsed from the file, ignoring comments
   and blank lines.

---

### Requirement 5: Failed-Login Lockout (`pam_faillock`)

**User Story:** As a maintenance coordinator, I want to configure
account-lockout thresholds and query per-user lockout state, so that
brute-force attempts are contained automatically.

#### Acceptance Criteria

1. WHEN the coordinator sets a faillock directive (`deny`,
   `unlock_time`, `fail_interval`, `even_deny_root`, …) THE SYSTEM
   SHALL upsert the directive in `/etc/security/faillock.conf`,
   idempotently.
2. WHEN the coordinator queries a user's lockout state THE SYSTEM
   SHALL invoke `faillock --user <username>` and return a
   `FaillockState` record with `user`, `recent_failures`,
   `locked: bool`.
3. WHEN the coordinator resets a user's failed-count THE SYSTEM
   SHALL invoke `faillock --user <username> --reset`.
4. WHEN `even_deny_root` is changed THE SYSTEM SHALL be explicit in
   the returned `AuthActionResult.detail` field about the risk, so
   reports flag the change prominently.

---

### Requirement 6: Login Resource Limits (`/etc/security/limits.*`)

**User Story:** As a maintenance coordinator, I want to declare
per-user and per-group resource limits (open-files, processes, stack
size, memory lock, priority) so that users cannot exhaust shared
system resources.

#### Acceptance Criteria

1. WHEN the coordinator sets a limit THE SYSTEM SHALL add or update
   the line `<domain> <type> <item> <value>` in a named drop-in file
   under `/etc/security/limits.d/<name>.conf`.
2. WHEN the requested limit already exists with the same value THE
   SYSTEM SHALL return `SKIPPED`.
3. WHEN the coordinator removes a limit THE SYSTEM SHALL strip the
   matching line from the drop-in file; when the file becomes empty
   THE SYSTEM SHALL delete it via `rm -f`.
4. WHEN the coordinator queries the effective limits THE SYSTEM
   SHALL aggregate `/etc/security/limits.conf` and every file under
   `/etc/security/limits.d/` into a `list[LimitEntry]`.

---

### Requirement 7: NSS Source Ordering (`/etc/nsswitch.conf`)

**User Story:** As a maintenance coordinator, I want to inspect and
adjust the NSS database source order, so that directory lookups
prefer the intended backend (files, sss, ldap).

#### Acceptance Criteria

1. WHEN the coordinator queries nsswitch THE SYSTEM SHALL parse
   `/etc/nsswitch.conf` into a `dict[str, list[str]]` keyed by
   database (`passwd`, `group`, `hosts`, …).
2. WHEN the coordinator sets the source order for a database THE
   SYSTEM SHALL rewrite the single matching line in
   `/etc/nsswitch.conf`, preserving every other line and any
   trailing comments.
3. WHEN the requested source order already matches the current file
   THE SYSTEM SHALL return `SKIPPED`.
4. WHEN `3-identity-management` manages nsswitch as part of an
   `authselect` profile activation, callers MUST NOT drive the two
   features at the same time against the same databases — the
   seam is caller-enforced.

---

### Requirement 8: Dry-Run, Elevation, and Error Reporting

**User Story:** As a maintenance coordinator, I want every mutating
operation to respect dry-run mode, run with declared elevation, and
surface failures with the underlying `exit_code` and `stderr`.

#### Acceptance Criteria

1. WHEN `config.dry_run=True` THE SYSTEM SHALL NOT execute any
   mutating command and SHALL return `AuthActionResult(status=DRY_RUN,
   command=<would-have-dispatched>)`.
2. WHEN `config.elevated=True` THE SYSTEM SHALL dispatch mutating
   commands with `elevated=True` to the command runner.
3. WHEN the runner returns a non-zero exit code THE SYSTEM SHALL
   return `AuthActionResult(status=FAILED, exit_code=<code>,
   stderr=<captured>)`.
4. THE SYSTEM SHALL NOT catch `SemanticError` or propagate silently;
   error semantics match the rest of the package.
